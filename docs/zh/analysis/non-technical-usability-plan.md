## 摘要

Trunkline 的骨架是对的：三角色模型清晰、业务流四段闭环、员工侧术语人话化已经落地、密钥页的统计口径与空态出口规范都超出了同类企业控制台的平均水平。

但实测代码后发现，**当前体验的主要阻力不来自"缺少功能"，而来自五处结构性错位**：

1. **认知错位——计价口径与用户心智模型不一致。** 后端按**厂商模型名**计价（`BillingService.java:35-37`），但管理员的心智是"我建了虚拟模型 company-main，所以要给 company-main 配价"。产品已用全局告警提醒（`PricingQuotaPanel.vue:22`、`TeamUsageView.vue:62-69`、`MyBillsView.vue:179-184`），但**缺价是逐行静默的**：一个虚拟模型挂 3 个成员、只配了 1 个的价，另外 2 个的调用静默计 ¥0，UI 从不指出。
2. **入口错位——熔断/限流有配置位，但 tab 名字不搭。** `PricingQuotaPanel.vue:96-135` 有完整的熔断开关+阈值弹窗、限流开关+阈值弹窗，但它们被塞进名为「价格与额度」的 tab，且和价格挤在 9 列表格中。非技术管理员会合理地认为"熔断不在这里配"。
3. **文案错位——策略中心的菜单副标题在撒谎。** `menu.ts:175` 写着"路由规则 / 多模型分工 / 模型挂了怎么办 / 新员工默认额度"，但 `StrategyView.vue:6-18` 的注释明确写着后三项**已在 v3.6 迁往「全局配置」**。菜单承诺了 4 件事，页面只提供 1 件。
4. **重复错位——同一功能两套实现，其中一套是纯 mock。** `/models`（`ModelsView.vue` 3 tab）与 `/providers`（`ProviderConsoleView.vue` 2 tab）是两套接入管理；前者 URL 可直达，其「💰 价格与额度」tab（`ModelPricing.vue` 95 行）是**硬编码假数据、保存按钮不写库**。用户改完价格点保存、弹窗关闭、刷新还原——**用户会以为自己的配置生效了**。这比"页面缺失"更严重：缺失的页面只会让人困惑，会骗人的页面让人基于假数据做决策。
5. **反馈错位——撞墙零反馈。** `router/index.ts:277-285` 无权访问时静默跳 `/my-quota`，无 403 页、无 toast、无说明。ops 点「全局配置」→ 页面变成「我的额度」，他会以为系统坏了。叠加 `FailureExplainer.vue` 的 6 个「去修复」链接有 3 个指向失效路由，"给出口"的机制本身也在骗人。

**好消息是：几乎所有需要的能力都已经存在，只是没被组织好。** 实测确认：

- `FailureExplainer.vue`（121 行）已把「人话解释 + 去修复出口」跑通，只是关在调用观测一页，且 3 个落点已失效；
- `QuickStartWizard.vue`（**1080 行**）已是完整的**管理员四步接入向导**（选厂商 → 填密钥 → 导入模型 → 自动建分组+测试密钥+复制 curl），挂在 `/quick-start` 却**不在菜单里**；
- `ProviderManagement.vue`（B 套）已有**状态驱动的三态下一步引导**，比菜单入口那套更强——这是一次重构时的**能力回退**；
- `provider.onboarding.*` 与 `provider.nextStep*` 共 17 条 onboarding 文案已成体系。

**所以本方案的主线不是"新建"，而是"收拢 + 接上 + 纠正"**：把已有的向导、引导、解释器接到正确的位置上，把失效的落点修好，把会骗人的 mock 页下线。

本方案给出 **P0 19 条 / P1 32 条 / P2 18 条**可执行改进，其中 **P0 中 15 条为纯文案/纯前端**（低风险、可单周上线），覆盖全部 16 个菜单项 + 1 个新增菜单项，并为 5 个核心页给出页面级布局方案。

## 一、角色画像与任务场景

### 1.1 user — 员工（非技术用户）

| 维度 | 刻画 |
|---|---|
| **他是谁** | 销售/市场/HR/财务等业务岗，偶有技术背景但不做开发。可能在 50–2000 人企业里被统一开通了 AI 网关账号 |
| **技术水平** | 会用 ChatGPT / DeepSeek 网页版与桌面客户端；**不知道** API Key、Base URL、Token、模型参数是什么，但**见过**这些词并知道它们"很贵" |
| **每天要做什么** | ① 看这个月还能用多少；② 把密钥填进自己常用的 AI 工具（Cherry Studio / Cursor / ChatBox）；③ 偶尔测试一下新装的工具通不通；④ 偶尔问"我这个月花了多少" |
| **核心任务清单**（用"要完成什么"描述） | · 确认公司给我的 AI 额度还够不够<br>· 拿到一把能用的密钥<br>· 把密钥装进我常用的工具里并确认能用<br>· 看懂这个月花了多少钱 |
| **他最怕什么** | · 不知道"钱"是怎么没的——用着用着发现被限流了，以为是软件坏了<br>· 报错看不懂（"connection refused"、"no available provider"、"熔断"）→ 不知道该找谁<br>· 自己的工具突然不能用，以为是自己配错了，反复瞎调 |
| **最容易卡在哪** | · 「申请密钥」点了没反应（只有一句 toast）→ 不知道要等多久、去哪问<br>· 「快速上手」第 3 步只有文字描述自己的工具要怎么填 → 找不到对应的那一栏<br>· 报错弹窗是英文或技术黑话 → 直接放弃 |

| 维度 | 刻画 |

### 2.1 ① 接入厂商

**断点清单**：

| # | 断点位置 | 卡住的原因 | 后果 |
|---|---|---|---|
| 2.1 | 创建对话框 | **创建态不能设策略、不能设启用状态**（`PoolManagement.vue:139`、`:154` 都带 `v-if="isEdit"`），只能创建后再点「编辑」补 | 两次弹窗、两次保存、两次心智切换；"创建"和"编辑"是同一个对象的两个半成品 |

### 2.3 ③ 创建密钥

**目标（用户视角）**：给某个员工发一把钥匙，限定他能用哪些模型、每月能花多少。

**当前实际路径**：
`团队 → 全部密钥` → 「创建密钥」→ 填用途 → 选持有人 → 勾选可用虚拟模型 → 填每月额度（¥ 输入框，或在无价格时退化为 token 输入框）→ 「高级设置」折叠（权限门控 / keyId / 有效期）→ 提交 → 弹窗显示一次明文

**断点清单**：

| # | 断点位置 | 卡住的原因 | 后果 |
|---|---|---|---|
| 3.1 | 表头与统计卡 | 统计卡口径是 总数/本月活跃/即将到期/**发了没人用**（`ApiKeyManagement.vue:13-28`），但页面**没有任何"待处理"聚合视图**——四个数字只是数字，不是任务 | 管理员看到"发了没人用 12 把"，不知道要逐条去查还是能批量处理 |
| 3.2 | 每月额度输入框 | `:disabled="formPrice === null"`，**取决于成员是否配了价**。没配价 → 管理员只能填 token 数；配了价 → 只能填 ¥。而 `formPrice` 的来源是"可用虚拟模型的加权均价"（`MyKeysView.vue:102-116` 同口径） | 同一个表单字段，时而是金额时而是非货币，且**表单不解释为什么这次是 token 那次是 ¥** |
| 3.3 | 「可用虚拟模型」勾选 | 勾选框旁有 `mismatched` 警告 tag 与 `permissionMismatchHint` alert | 这是好设计，但**警告文案没说"这意味着什么"**——是"员工调用会 403"还是"会降级"？ |

| 3.5 | 密钥明文 | 只返回一次（`:661` `showKeyValueDialog`），这是安全正确设计 | 但**没有"复制后我关掉了，还能再拿到吗"的说明**，也没有"怎么把它安全给到员工"的指引 → 管理员容易把明文贴进群聊 |

| 3.6 | 与「我的密钥」并存 | ops 视角在 `/all-keys`，自己的密钥在 `/my-keys` | admin 角色同时可见两个（`menu.ts:66`、`:87` 都含 admin），但菜单里分处「我的」和「团队」两组，且文案没说清区别 |

**理想路径**：
`团队 → 全部密钥` → 顶部改为**任务流**而非统计卡：「12 把没人用（可批量停用）｜ 3 把 7 天内到期（可批量续期）｜ 2 把已过期（建议停用）」，每条都是可点击的批量操作入口 → 「创建密钥」表单改为「选人 → 选模型（带价格预览：这个模型约 ¥0.12/千）→ 定额度（**默认按 ¥，并显示"≈ 100 万字/月"的人话折算**）→ 高级（折叠）」。

### 2.5 跨段衔接断点（重点）

**实测硬证据**：grep `下一步|nextStep|goCreate|去创建|去配置|继续创建|建池|建模型` 覆盖 `views/providers/` + `views/config/pools/` + `views/security/ApiKeyManagement.vue`，命中**仅 3 处，且全部在添加供应商向导内部**（`ProviderConsoleView.vue:221` tooltip、`:270` 步骤条按钮、`:703` 代码注释）。
→ **向导内的"下一步"存在，但向导结束后没有"下一步该干什么"的引导。**

> **补充勘误**：上述 grep 未覆盖 `views/models/`（B 套）。实测 `ProviderManagement.vue:412-424` **有**三态 `nextStepHint(p)`（没 Key → 去设 Key；没模型 → 去加模型；有模型 → 去创建密钥）+ 空态三步 onboarding 块（`:118-147`）。
> → **结论修正**：不是"整套产品没有下一步引导"，而是「**新入口 A 套（菜单入口）丢掉了旧入口 B 套已有的引导能力**」。这是一次**重构时的能力回退**，不是从未做过。
> → **产品判断**：B 套的 `nextStepHint` 三态判定逻辑（`hasApiKey` / `modelCount` / 都有）**正是本方案 §5.3 想要的"状态驱动待办"**，只是判定维度少了「是否配价」「是否建虚拟模型」。**应把 B 套的三态逻辑搬回 A 套并扩充**，零新增成本。

| # | 衔接点 | 第①段结束时用户手里有什么 | UI 有没有告诉他下一步 | 缺口 |
|---|---|---|---|---|
| X1 | ①→② | 供应商 + N 个已接入的厂商模型 | 有。引导卡第 3 步「建虚拟模型 →」`router.push('/model-pools')` | ✅ 有路标，但**引导卡是静态的**，第 4 步永远显示"去建 →"占位文字，不表示"你现在该做这个"。应改为**按状态驱动的待办卡**（移植 B 套 `nextStepHint` 三态逻辑并扩充） |
| X2 | ①→②（价格） | 已接入的模型**但可能没配价** | **完全没有**。价格与额度 tab 不提示"这 N 个模型还没配价" | ❌ **最严重的衔接断点**。管理员完成接入 → 建虚拟模型 → 发密钥 → 员工开始用 → 账单 ¥0 → 无人知道原因 |
| X3 | ②→③ | 虚拟模型"公司主力"（含成员、策略、配额） | 有。`ProviderConsoleView.vue:527-534` 第 4 步「发密钥给员工」`router.push('/all-keys')` | ⚠️ 有路标，但**未携带上下文**——跳到「全部密钥」时不知道是要为"公司主力"发密钥 |
| X4 | ③→④ | 密钥创建成功，**明文只显示一次** | 无。弹窗显示明文后就结束，没有"怎么给到员工"的指引 | ❌ 管理员拿着明文不知道下一步。是自己复制给员工？还是让员工自己来申请？两条路产品里都半成品 |
| X5 | ④→（员工首用） | 员工登录 | 员工默认落到 `/my-quota`（`router/index.ts:41` redirect） | ⚠️ 「我的额度」不是"下一步"。员工的首要动作是"装上密钥"，但**「快速上手」在菜单第 3 位，首屏看不见** |
| X6 | 权限边界 | ops 建了虚拟模型 | 「账号与权限」页管的是**账号角色**，与**密钥的 allowedGroups** 是两套独立的授权机制 | ⚠️ 管理员配了角色权限以为员工就能用，但员工仍需一把带 `allowedGroups` 的密钥。两套授权无交叉说明 |
| **X7** | **①（规则告知）** | 刚接入厂商，什么都还没建 | **有规则、无出口**。`ProviderConsoleView.vue:51` 那句「员工不能直接调用刚接进来的厂商模型——必须先建成虚拟模型才能用，这样才能统一管控成本和审计。」**说清了规则，但没有任何按钮或跳转** | ❌ **最高杠杆的一处**：这句是全项目最好的业务解释，却以**纯告警条**形式呈现（`el-alert type="warning"`），用户读完不知道下一步该点哪。**应升级为带行动按钮的引导条**（见 §3.6） |
| **X8** | **③（密钥→员工）** | 密钥已建，明文在手 | 无任何告知。`ApiKeyManagement.vue:661` 的明文弹窗显示完就结束 | ❌ 管理员不知道"接下来把这个密钥给员工，并告诉他填在哪个工具里"。唯一相关的是员工侧 `MyKeysView.vue:181` 的「申请功能尚未接入，请联系管理员」——**但那是员工视角**，管理员这边什么都没有 |

**跨段衔接的通用设计原则（写入 §3.6 与 §5.3）**：
> 每一段结束的那一刻，UI 必须回答两个问题：**「我刚完成了什么」**（里程碑）+ **「我接下来该做什么」**（出口，含按钮文案与落点）。
> 缺任一半，这一段就是断的。

### 3.7 撞墙体验：无权限时应该看到什么

> **现状（已实测确认）**：`router/index.ts:277-285` 无权访问时 `return { name: 'my-quota' }`——**静默跳转到员工额度首页，无 403 页、无 toast、无任何说明**。
> **实际后果**：ops 点「全局配置」（admin 专属）→ 页面变成「我的额度」。他会以为系统坏了或自己被降权了，**完全不知道是哪个菜单项被拦、为什么**，而且跳过去的页面语义完全不相干，困惑感被放大。这是典型的**死路**：没有出口、没有解释、无法自救。

#### 3.7.1 产品形态推荐：**独立 403 页面 + 页面内的权限提示**，不是 toast

| 候选 | 评价 |
|---|---|
| **toast 提示** | ❌ 不推荐。toast 3 秒消失，用户往往正在操作别的页面根本看不见；且跳走了就没有载体承载"找谁开"这条信息 |
| **独立 403 页面** | ✅ **推荐**。它是一个**有地址、可收藏、可分享**的载体，能承载完整的"为什么 + 找谁 + 怎么办"，也便于运维把链接直接发给管理员申请开通 |
| **跳回上一页 + 弹窗** | ⚠️ 次选。适合"点菜单被拦"的场景，但对"直接敲 URL / 收藏旧链接"的场景无效（没有上一页可回） |

**推荐形态**：无权限 → 跳 `/403?from={path}&missing={permissionCode}`，页面内容如下：

```
┌──────────────────────────────────────────────┐
│  你没有权限查看这个页面                        │
│                                               │
│  你刚才访问的是：全局配置                       │
│  缺少的权限：系统设置管理                       │
│                                               │
│  这个页面用于配置全公司的默认规则，             │
│  通常只有系统管理员需要。                       │
│                                               │
│  [ 联系管理员开通 ]  ← 复制一段申请文本        │
│  [ 回到我的额度 ]                              │
└──────────────────────────────────────────────┘
```

**提示文案必须包含的 4 项信息**：

| # | 信息 | 示例 |
|---|---|---|
| ① | **被拦的是哪个页面** | `你刚才访问的是：全局配置` |
| ② | **缺什么权限**（技术名 + 人话） | `缺少的权限：系统设置管理`（人话）＋ 括号内 `system:accounts:manage`（技术名，便于管理员查） |
| ③ | **这个页面是干什么的** | `这个页面用于配置全公司的默认规则，通常只有系统管理员需要。` |
| ④ | **找谁开** | `联系管理员开通` 按钮 → **复制一段现成的申请文本**：`你好，我需要「全局配置」页面的权限（system:accounts:manage），用于配置 ______。` —— 一键复制，无需手打权限码 |

#### 3.7.2 菜单项的可见性策略：隐藏 vs 置灰

**现状**：菜单可见性已按 `permission` + `roles` 过滤（`menu.ts` 的可见性逻辑），无权的人**根本看不到菜单项**。

**两种策略的对比**：

| 策略 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **隐藏（现状）** | 界面干净，不制造"我能但不能"的挫败 | **用户不知道有这个东西存在** → 别人告诉他后他输 URL → 被静默跳走 → 困惑 | 绝大多数功能 |
| **置灰 + 提示缺权限** | 用户知道存在、能申请 | 菜单变长（16 项里可能有 3-4 项是灰的），非技术管理员看到一堆灰条会以为系统坏了 | **少数"用户明确知道自己需要"的场景** |

**推荐**：**保持隐藏为主**，但对**跨角色高频页面**（如「全局配置」在 ops 侧会用到）采用置灰 + 提示。
具体做法：菜单项新增可选字段 `requiresPermission?: string`（当 `roles` 不含当前用户但 `permission` 也无时，**置灰但可点击**），点击后走 403 页。

> 理由：非技术管理员最怕的不是"看不到"，而是**"我明明点得进去 / 别人说能进，但就是进不去且没人告诉我为什么"**。置灰至少给了一个**可解释的、可点击的、指向答案的**入口。

#### 3.7.3 附带修掉的一个漏洞

`router/index.ts:275-290` 的守卫逻辑是：
```ts
const menuItem = menuGroups.flatMap(g => g.children).find(c => c.path === to.path)
if (menuItem) { /* 按 permission / roles 判定 */ }
const required = to.meta.permissions   // 非菜单路由才走这里
```
→ **未被菜单收录的路径（`/models`、`/quick-start`、`/keys`、`/quota` 等）因为 `menuItem` 为 undefined，落到了 `meta.permissions` 分支**。`/models` 恰好**也没有** `meta.permissions` → **直接放行**。

**修法（与 P0-11 同一处改动）**：
1. `/models` 等 B 套路由 → **下线并重定向到 `/providers`**（见 §3.8），从根上消除这条"隐藏可达路径"。
2. 守卫增加一条**兜底**：`to.path` 不在菜单内**且**不在**显式白名单**（`/login`、`/guide`、`/docs`）时，一律查 `to.meta.permissions`，**没有 `meta.permissions` 的路由视为需要 `config:instances:read`**，不得裸奔。

### 3.9 页面目标说明：全局约定 + 16 条 subtitle 建议文案

> **现状**：`PageHeader` 在 35 处使用，但只有 10 处（29%）传了 `:subtitle=`；说明文案的自造实现有 4 种并存（`page-tip` / `page-heading__sub` / PageHeader `subtitle` prop / `menu.ts` `subtitle`）。
> **而 `menu.ts` 的 16 条 `subtitle` 是死数据**——`ConsoleLayout.vue:159-180` 渲染菜单只输出 `{{ item.title }}`，从不读 `item.subtitle`。16 条精心写的说明**全部不可见**。

#### 3.9.1 三条约定

| # | 约定 | 理由 |
|---|---|---|
| **G1** | **统一到 `PageHeader` 的 `subtitle` prop**。不再新增 `page-tip` / `page-heading__sub` 这类平行实现 | `PageHeader` 已是事实标准（35 处使用），有现成样式 `.page-header__subtitle`。平行实现越多，风格越碎 |

### 3.11 员工侧可见范围的收窄

> **事实**：`MyKeysView.vue:16,81-93` 调 `getPoolList()`（`/config/pools/list`，管理员级端点），取回**全公司所有虚拟模型**及其成员 `instanceId`，用途是**算这个密钥的混合单价**。员工因此能看到公司全部虚拟模型名 + 内部实例 ID，**与该密钥白名单无关**。

#### 3.11.1 用户视角应该看到什么

**主张：员工侧只显示该密钥白名单内的虚拟模型，一个不多一个不少。**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **① 只显示白名单内**（推荐） | ①语义正确——「可用模型」就是能用 ②不泄露公司其他模型名 ③"这个我能用吗"的困惑自然消失 | 需要一个只返回白名单相关信息的接口，或前端过滤 |
| ② 保持现状（显示全部） | 零改动 | ①员工看到"财务模型""法务模型"却不能用 → 困惑 ②信息泄露 ③"可用模型"列名与内容不符 |

**推荐 ①**，落地方式二选一（需架构师确认后端权限）：
- **前端过滤**：`getPoolList()` 结果按 `key.allowedGroups` 取交集后使用（**零后端改动**，但仍下载了全量数据——**只解决了显示，没解决传输**）
- **后端收窄**（更彻底）：新增 `GET /api/auth/api-keys/mine` 返回体里直接带 `allowedGroups` 的**显示名与价格**（员工无需自行算）→ **顺带解决混合单价口径问题**

#### 3.11.2 混合单价口径变化的用户可感知影响

| 口径 | 含义 | 员工看到什么 |
|---|---|---|
| 现状（白名单外的模型参与加权） | "公司全部模型的均价" | 一个**与自己无关**的数字——员工看到"本月已用 ≈ ¥12"，但这个数字是他用不了的模型的均价算出来的 |
| 收窄后（只算白名单内的模型） | "**我这把密钥能用的模型**的均价" | 一个**与自己直接相关**的数字 |

**产品判断**：数字会变，但**变的是对的**。现状下的金额是"用一个他用不到的模型的均价去折算他的用量"——这个数字本身就没有业务含义。
**必须在 UI 上说明**，否则员工会以为账单算错了。文案：`≈ 按你能用的模型均价估算`（放在金额副标题旁，`MyKeysView.vue:225-229` 的 `dual-cell__sub` 位置）。

#### 3.11.3 「白名单」这个词本身要处理

#### 3.12.2 是否需要任务导向的入口？

**需要，但不需要新建入口——应该改的是"搜索什么"。**

非技术管理员的心智模型是任务式的（"我要接个新厂商"），菜单是功能式的（"接入管理"）。二者之间需要一个映射层。

#### 3.12.3 一个反向建议：**不要**把任务向导塞进命令面板

任务式**引导**（如"我要接入新厂商"→ 跳到 `/quick-start` 向导）应该放在**页面内的引导卡**（§3.5.1 区块②）和**待办卡**里，而不是命令面板。理由：命令面板是**导航工具**，用户搜"接厂商"是想**去那个地方**，不是想**被一步步引导**。两件事混在一起会让命令面板变成一个不可预测的东西。

> **例外**：「快速接入」向导本身（`/quick-start`，见 §5.1）作为**菜单项**加进「团队」组顶部即可——它是导航目标，不需要命令面板特殊对待。

## 四、术语解释体系设计

### 4.1 分层策略：四档

| 档 | 判定标准 | 处理方式 | 例子 |
|---|---|---|---|
| **L1 必须人话化** | 员工**日常会读到**且**理解它不影响正确使用** | 直接换词，不加解释 | Token 用量→已用量；白名单→可用范围；Max Tokens→最长回复；实例→（员工侧不出现） |
| **L2 人话化 + 一句话解释** | 员工**偶尔读到**且**不理解会做错事** | 换词 + 首次出现处加一行小字 | "额度上限（这张卡最多能用的量）"；"密钥（填进 AI 工具的那串密码）" |
| **L3 保留技术词 + tooltip** | 员工**不该遇到**，但 ops/admin 需要精确度 | 保留原词，配 tooltip 补充"这是什么/为什么" | 熔断阈值（tooltip："连续失败几次就把模型临时踢出轮询"）；副本（tooltip："网关跑了几份，统计可能只覆盖其中一份"） |
| **L4 不管** | 纯内部实现细节，用户无需知晓 | 原样保留，不加解释 | Base URL（ops 侧是必填项，加 tooltip 即可，不做员工侧映射） |

**L1/L2 的员工侧词表已在 `constants/employeeTerms.ts:34-141` 建立**，本方案**不重新发明**，只做两件事：
1. **补缺**：现有词表缺「额度上限」「密钥」「模型池/虚拟模型」的员工侧解释型词条；
2. **扩面**：`STAFF_ONLY_TERMS`（`:152-170`）当前是一张"员工页禁止出现的词"黑名单，本方案把它**同时用作 ops 侧的"这些词必须有 tooltip"白名单**——一张表，两个用途，一个验收源。

### 4.2 解释文案放在哪：四类载体

| 载体 | 何时用 | 实例 |
|---|---|---|
| **tooltip（`el-tooltip`）** | 术语出现在表格列头、表单项、按钮旁，且解释 ≤ 30 字 | 「熔断」列头 → "连续出错就临时踢出这个模型"；「按权重随机」→ "权重高的被选中的机会更大" |
| **行内说明（form-tip / hint 小字）** | 表单字段旁的口径说明、单位、后果 | 单价输入框下："¥ / 千 token。输入 = 你说的话，输出 = 模型的回答" |
| **空态（`el-empty` + 出口按钮）** | 列表为空、且用户有下一步可做 | 「还没有虚拟模型」→「先去接入厂商」；「还没有路由规则」→「大多数情况不需要它」 |
| **独立帮助（页头 `help-link`）** | 整页职责边界说不清，需要一整段 | 「策略中心」`help-link="/guide"` 已有；建议在 `/guide` 增加「四步开通 AI 能力」章节 |

**已有基线直接沿用**：
- `components/common/ClusterScopeNotice.vue` —— 副本范围提示，**单机部署不渲染**（这个"不想显示就别渲染"的克制应保持）
- `utils/effectScope.ts` —— 生效时间提示，`effectMessage('已保存', 'config')` 追加"其余副本需重启或再保存一次"。**口径是"宁可说得难听也不给安慰话"**，本方案的文案一律遵循此原则

### 4.3 扩展到 ops 侧：**扩展既有 `constants/glossary.ts`，不新建并行表**

> **【v3 修正】** 本节原提议新建 `constants/opsTerms.ts`。架构师勘察发现**既有机制已存在**：`frontend/src/constants/glossary.ts`（`GLOSSARY` 词条表 + `GlossaryEntry { zh, en }`）与 `components/common/TermHelp.vue`（问号图标组件，直接 `GLOSSARY[props.term]` 取文案）。实测现有词条 **10 个**：`slowQuery` / `minCount` / `samplingRate` / `span` / `circuitBreaker` / `halfOpen` / `hashAlgorithm` / `virtualNodes` / `weight` / `tokenQuota`。

> **理由**：两套并行的术语机制会让后续开发者不知道该用哪一套；`TermHelp.vue` 的问号图标交互已经验证过，是现成的 L3「保留技术词 + tooltip」载体。

### 4.6 员工侧错误分层（补齐测试场以外的页面）

**现状**：`views/playground/utils/errorHandler.ts:87-104` 已有关键词→人话映射（`EMPLOYEE_KEYWORDS`），只在测试场生效。`utils/request.ts:84-87` **反向操作**——把后端 message 提升到 `error.message`，导致后端技术文案直达员工。

> **与 §3.10 的关系**：`FailureExplainer.vue` 已经把「人话解释 + 去修复出口」这个模式跑通了（结构化 props 判定），`errorHandler.ts` 走的是**字符串关键词匹配**。
> **两者判定逻辑高度重叠**（都按 熔断/限流/配额/401/403/5xx/超时 优先级）。
> **推荐合并为一个组件**：`FailureExplainer` 增加 `rawMessage?: string` prop，**结构化判定优先、关键词匹配兜底**；`errorHandler.ts` 的 `EMPLOYEE_KEYWORDS` 作为兜底映射表移入 `failureExplain` 命名空间，`errorHandler.ts` 删除。
> 这样全站只有**一处**错误解释逻辑，验收也只有**一处**要查。

**方案**：在 `FailureExplainer` 基础上抽出**全局单点** `utils/friendlyError.ts`（供 ElMessage 等无组件上下文处调用）：

```ts
// utils/friendlyError.ts（新增）
export function friendlyError(err: unknown): string {
  if (isStaff()) return rawMessage(err)          // ops/admin 看原始报错
  const raw = rawMessage(err)
  const hit = matchFailureKey(raw)                // 复用 FailureExplainer 的关键词表
  if (hit) return failureExplain(hit, 'employee') // 员工口径
  return employeeTerm('serverError')              // 兜底：员工侧永不暴露原始技术文案
}
```

**员工页统一改造点**（5 处裸 `ElMessage.error`）：
- `views/my/MyKeysView.vue:42`
- `views/my/MyQuotaView.vue:256`
- `views/my/MyBillsView.vue:95`、`:98`
- `views/my/QuickstartView.vue:70`

**改造后员工看到什么 vs 运维看到什么**：

| 场景 | 员工（user）看到 | 运维（ops/admin）看到 |
|---|---|---|
| 密钥无效 / 401 | 「你的密钥不能用了，请联系管理员重新发一把」 | 原始报错 + `FailureExplainer`：「密钥无效或已过期」+ [去密钥管理 →] |
| 触发限流 / 429 | 「请求有点太快了，等几秒再试」 | 「调用过于频繁，触发了限流保护」+ [去调限流 →] |
| 额度用尽 | 「本月额度已经用完了，请联系管理员调整上限」 | 「今天的 Token 额度已用完」+ [去密钥管理 →] |
| 模型熔断 | 「这个模型暂时不可用，请稍后再试；一直不行就联系管理员」 | 「该实例已熔断，暂时被摘除以保护后端」+ [去看熔断 →] |
| 上游 5xx | 「服务出了点问题，请稍后重试；一直不行就联系管理员」 | 「上游模型服务返回了错误」+ [去查实例 →] |
| 未识别错误 | 「服务出了点问题，请稍后重试；一直不行就联系管理员」+ **错误码**（供转交管理员） | 原始技术报错全文（含堆栈线索） |

**验收**：`verify-employee-terms` 脚本的检索范围从"员工页面渲染文本"扩展到"员工页面所有错误提示来源"——即 `utils/request.ts` 提升的 message 在员工侧路径下**必须**先过 `friendlyError` / `FailureExplainer`。

#### 5.1.3 关于 `views/_attic/OnboardingSteps.vue` 的判断

> **结论：模式复用，内容不复用。**

**它是什么**（160 行）：一个**步骤条**组件（`currentStep` prop 驱动，四态样式：已完成 ✓ / 进行中 / 待办 / 箭头分隔），点击任一步骤可跳转。步骤内容写死为 4 步（`OnboardingSteps.vue:46-51`）：

| 步 | 旧文案（`onboarding.json`） | 落点路由 |
|---|---|---|
| 1 | 选择协议适配 | `/protocol-adapters` |
| 2 | 创建模型分类 | `/model-categories` |
| 3 | 接入模型 | `/models` |
| 4 | 测试连通 | `/playground` |

**为什么被废弃**：这 4 步是 **v3.5 之前的信息架构**（适配器 → 模型分类 → 实例）。v3.5 重构后业务流变成了 **接厂商 → 建虚拟模型 → 发密钥 → 员工使用**，而「协议适配器」「模型分类」已下沉到「系统 → 模型配置」（admin 专属），不再是业务流主线。**所以它不是"样式过时被搁置"，是"内容被新的业务流取代"**。

**产品判断**：

| | 判断 |
|---|---|
| **内容（4 个步骤）** | ❌ **不复用**。已经与当前业务流不符，且前两步指向 admin 专属页面，普通 ops 进去会撞 403（见 §3.7） |

**结论**：**不复活 `OnboardingSteps.vue`，但把它的视觉模式搬到新的 `SetupProgress.vue` 上**；`OnboardingSteps.vue` 本身随 `_attic` 一并删除（见 §3.13.4）。
**理由写明，避免后续开发者误以为漏做**：它的 4 个步骤对应的是已被取代的旧信息架构，且第 3 步指向的 `/models` 本身就要下线。

### 5.5 空态三要素模板（全局约定）

**三要素**：

| # | 要素 | 要求 | 反例 | 正例 |
|---|---|---|---|---|
| ① | **现状说明** | 一句人话，说清"现在是什么" | 「暂无数据」 | 「你名下还没有密钥」 |
| ② | **原因** | 说清"为什么会有这个状态"——让用户知道**这是正常的初始状态还是出错了** | （缺失） | 「领到密钥后才能在自己常用的 AI 工具里调用公司 AI」 |
| ③ | **出口** | 至少一个按钮，指明**下一步做什么 + 落点** | 只有一段文字 | 「申请一个密钥」→ 打开申请弹窗 |

**按页面套用示例**：

| 页面 | ① 现状 | ② 原因 | ③ 出口 |
|---|---|---|---|
| 我的密钥 | 你名下还没有密钥 | 领到密钥后才能在自己常用的 AI 工具里调用公司 AI | [申请一个密钥] |
| 我的额度 | 本月还没有调用记录 | 用一次就会出现在这里——去「测试场」试一句 | [去测试场试一次] |
| 全部密钥 | 还没有给员工发过密钥 | 员工拿到密钥才能调用公司 AI。先建一个虚拟模型，再来发密钥 | [去建虚拟模型] |
| 虚拟模型 | 还没有虚拟模型 | 虚拟模型是给员工用的对外名字，员工不能直接调厂商模型 | [先去接入厂商]（若已有厂商则 [新增虚拟模型]） |
| 接入管理 | 还没有接入任何供应商 | 接入后要给模型配价格，员工才能用 | [添加供应商] |
| 策略中心 | 还没有路由规则 | **大多数情况下你不需要它**——虚拟模型已经能处理故障转移了 | [去建虚拟模型] |
| 团队用量 | 本月还没有用量 | 员工开始调用后这里会有数字 | [看看接入管理]（或无出口，因这是正常态） |
| 调用观测 | 还没有调用记录 | 员工调用公司 AI 后，这里会逐条记录谁在什么时候调了什么 | [去发密钥] |
| 状态监控 | 网关运行正常 | 没有异常时这一页就是空的 | （正常态，无需出口） |
| 全局配置 | 使用默认配置 | 这些是网关级默认值，单个模型可单独覆盖 | [查看默认值说明] |

**规则补充**：正常态的空（如「网关运行正常」）**允许没有出口**，但必须有 ① + ②。**只有"没数据"而既无原因也无出口的空态，一律不合格。**
